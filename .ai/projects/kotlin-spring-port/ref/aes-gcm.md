## GCM 이 실제로 하는 일

> 계기: "node 에서 AES 대칭키 암호화/복호화는 여러 번 해봤는데 이건 그냥 암호화/복호화만 하는 게 아닌 것 같다".
> 맞다. **하는 일이 두 개**다. 실험 코드는 [`GcmDemo.java`](GcmDemo.java) — 아래 출력은 실제 실행 결과다.

### 1. CBC 와의 차이 — 일의 개수

| | CBC | GCM |
|---|---|---|
| 기밀성 (내용 숨김) | ✅ | ✅ |
| **무결성·인증 (변조 감지)** | ❌ | ✅ |
| 패딩 | 필요 (16바이트 블록 맞춤) | **불필요** (`NoPadding`) |
| 암호문 길이 | 16의 배수로 부풀려짐 | **평문과 동일** |
| 분류 | 단순 암호 모드 | **AEAD** (Authenticated Encryption with Associated Data) |

CBC 로 암호화한 쿠키는 클라이언트가 바이트를 뒤집어도 **복호화가 성공한다.** 서버는 "이게 내가 만든 토큰인지" 알 방법이 없다.
GCM 은 안 맞으면 **평문을 아예 내주지 않고 던진다** → `AEADBadTagException`. 완료 조건 5번이 검증하는 게 이 기능이다.

### 2. 태그 처리가 코드에 안 보이는 이유 (Node 대비)

Node 는 태그를 **손으로** 관리한다:

```js
const cipher = crypto.createCipheriv('aes-256-gcm', key, iv);
const encrypted = Buffer.concat([cipher.update(plain, 'utf8'), cipher.final()]);
const tag = cipher.getAuthTag();                  // ← 별도로 꺼낸다
return Buffer.concat([iv, encrypted, tag]);       // ← 직접 붙인다
// 복호화: decipher.setAuthTag(tag) 를 안 하면 final() 이 던진다
```

Java(JCE) 는 **태그를 암호문 뒤에 자동으로 붙여서** 반환한다. `getAuthTag()` 에 해당하는 API 가 없다.

```kotlin
val encrypted = cipher.doFinal(plain.toByteArray())   // 이미 [암호문 || 태그]
```

`GCMParameterSpec(128, iv)` 의 `128` 이 "태그를 128비트로 만들어 붙여라" 는 지시다.
그래서 태그 관련 코드가 한 줄도 없는데 태그는 있다.

### 3. 토큰의 바이트 배치

```
┌────────────┬──────────────────────────┬──────────┐
│  IV 12B    │  암호문 (평문과 같은 길이)  │  태그 16B │
└────────────┴──────────────────────────┴──────────┘
 ↑ 우리가 붙임   ↑                        ↑
                 └── doFinal() 이 한 덩어리로 반환 ──┘
```

- `iv + encrypted` — IV 를 앞에 붙이는 건 우리 일. IV 는 **비밀이 아니라서** 평문으로 붙여도 된다
- `require(decoded.size > IV_SIZE)` — 12바이트 이하면 IV 조차 안 되는 쓰레기. `doFinal` 전에 걷어낸다
- `doFinal(decoded, IV_SIZE, ...)` — 태그를 **따로 떼지 않는다.** JCE 가 "마지막 16바이트는 태그" 로 알아서 해석한다

**크기 계산**: 페이로드 45B → `12 + 45 + 16 = 73B` → Base64URL 약 98자.
오버헤드가 **길이 비례가 아니라 고정 28바이트**다. 필드를 추가해도 늘어나는 건 그 필드만큼.

### 4. IV 에는 무엇이 들어가나 — **아무것도 안 들어간다**

`SecureRandom` 이 뱉은 12바이트가 전부다. 사용자 ID·시각·어떤 구조도 없다. 요구되는 건 내용이 아니라 성질이다:

| 요건 | 왜 |
|---|---|
| **같은 키로 절대 반복되지 않을 것** | 유일한 진짜 요건 (6번 참고) |
| 비밀이 아니어도 됨 | 그래서 암호문 앞에 평문으로 붙여 보낸다 |
| 복호화 측이 알아야 함 | 그래서 **반드시** 같이 보낸다 |

**왜 12바이트인가** — GCM 은 내부에서 128비트 카운터 블록 `J0` 를 만든다. IV 가 96비트면 딱 맞아떨어진다:

```
J0 = [ IV 96비트 ] [ 00 00 00 01 ]
```

12바이트가 아니면 IV 를 GHASH 로 한 번 해싱해 `J0` 를 만들어야 한다. 동작은 하지만 **연산이 늘고 얻는 게 없다.**

### 5. 태그에는 무엇이 들어가나 — **계산되어 나오는 값**

태그는 데이터를 담는 자리가 아니다. **암호문 전체에 대한 MAC** 이다.

```
H  = AES_K(0으로 채운 16바이트)          ← 키에서 파생된 "해시 서브키"
J0 = IV ∥ 00000001

키스트림 = AES_K(J0+1), AES_K(J0+2), ...
암호문 C = 평문 P XOR 키스트림            ← 카운터 모드. 그래서 길이가 안 변한다

S    = GHASH_H( AAD ∥ 패딩 ∥ C ∥ 패딩 ∥ AAD길이(8B) ∥ C길이(8B) )
태그 = S XOR AES_K(J0)
```

**태그의 입력**:

| 입력 | 우리 경우 |
|---|---|
| **암호문** (평문이 아니다) | encrypt-then-MAC 이 공짜로 되는 이유 |
| **AAD** | 안 씀 (빈 값). 7번 참고 |
| **둘의 길이** (각 8바이트) | 바이트를 AAD↔암호문 사이로 옮기는 공격 차단 |
| **키** (`H` 와 `AES_K(J0)` 양쪽) | 키 없이는 태그를 계산할 수 없다 |
| **IV** (`J0` 를 통해 간접) | ↓ |

**IV 는 평문으로 노출돼 있는데 왜 못 고치나** — 태그 마지막 단계가 `XOR AES_K(J0)` 이고 `J0` 는 IV 에서 나온다.
**IV 를 1비트 건드리면 태그가 안 맞는다.** IV 를 따로 보호할 장치를 만들 필요가 없다. 실측:

```
─── ② 암호문 1바이트 변조 ───
  AEADBadTagException ← 잡아냈다
─── ③ IV 1바이트만 변조 ───
  AEADBadTagException ← IV 도 인증 범위 안에 있다
```

그리고 **태그는 난수가 아니다.** (키, IV, AAD, 암호문)이 같으면 항상 같은 태그가 나온다.
매번 달라 보이는 건 IV 가 달라서다.

```
─── ① 같은 평문·같은 키를 두 번 암호화 ───
1회차  IV = 702199565c0077f6cffeea80
      암호문 = 17b415f3194801bca9329c8d4fe842f3 (16바이트)
      태그  = d18811906b3b704af93e6d076c200ae6
2회차  IV = f7324c65105edb48f45998cd
      암호문 = 4db77e0395b2834f3741ed75bb57ffc7 (16바이트)
      태그  = 56692a3eec19487c4daaaceea302a9b4
```

### 6. IV 재사용이 치명적인 이유 — 두 단계로 무너진다

키스트림은 `f(키, IV)` 다. IV 가 같으면 키스트림이 **완전히 동일**하다.

```
C1 = P1 XOR KS
C2 = P2 XOR KS
C1 XOR C2 = P1 XOR P2      ← 키스트림이 소거된다
```

```
─── ④ IV를 재사용하면? ───
  암호문1 XOR 암호문2 = 00000000000000000000000000000003
  평문1  XOR 평문2   = 00000000000000000000000000000003
  → 완전히 일치. 암호문 차이가 평문 차이를 그대로 노출한다
```

**1단계 (평문 노출)**: 공격자는 키를 몰라도 두 평문의 차이를 안다. 한쪽을 알면 다른 쪽이 완전히 복구된다.
**2단계 (위조 가능)**: 여기가 CBC 보다 더 나쁜 지점이다. `H` 는 **키에만** 의존하므로, 같은 IV 로 만든 태그 두 개가 있으면
GF(2^128) 방정식을 풀어 **`H` 자체를 복구**할 수 있다. 그러면 **임의의 메시지에 유효한 태그를 만들 수 있다** —
무결성이 통째로 무너진다. 이 공격에 "forbidden attack" 이라는 이름이 붙어 있다.

⚠️ **`TokenCipher` 에서 IV 를 필드로 캐싱하는 순간 이게 발생한다.** `random` 은 필드, `iv` 는 지역변수여야 하는 이유.

> 96비트 난수 IV 의 충돌은 생일 문제라 **약 2^32회 암호화**부터 확률이 무시 못 할 수준이 된다.
> 로그인 40억 번이니 우리 규모에서는 고려 대상이 아니다.

### 7. 안 쓰고 있는 기능 — AAD

이름의 "AD"(Associated Data)가 남아 있다. **암호화하지 않으면서 인증 범위에는 넣는** 데이터를 붙일 수 있다.

```kotlin
cipher.updateAAD(userAgent.toByteArray())   // 우리는 안 쓰는 중
```

"이 토큰은 이 User-Agent 에서만 유효" 같은 걸 **토큰을 키우지 않고** 묶을 수 있다.
복호화 때 같은 AAD 를 안 주면 태그가 안 맞아 실패한다. 쿠키 탈취 대응을 얘기할 때 다시 나올 도구.

### 8. 왜 태그를 128비트로 (`TAG_BITS`)

위조 성공 확률이 정확히 **시도당 2^-태그길이** 다.

- 128비트 → 시도당 1/2^128. 사실상 불가능
- 32비트로 자르면 → 시도당 1/43억. 공격자는 **무한히 재시도할 수 있다.** 초당 수천 번이면 현실적 시간에 뚫린다

쿠키 크기 제한 4KB 에 여유가 넘치므로 줄일 이유가 없다.

### 9. 이게 **안** 해주는 것 (착각 방지)

- **서명이 아니다.** 대칭키라 키를 가진 쪽은 **누구나 위조할 수 있다.** 제3자 검증이 필요하면 비대칭(JWT RS256)
- **JWT 가 아니다.** 표준 헤더/클레임이 없어 다른 시스템이 해석 못 한다. 대신 **페이로드가 안 보인다** —
  JWT 는 서명만 하므로 Base64 를 풀면 내용이 다 보인다. 우리 건 JWE direct encryption 에 가깝다
- **만료를 모른다.** GCM 은 "이 바이트가 위조되지 않았다" 만 보증한다. 유효기간은 `expiresAt` 을 페이로드에 넣고
  `verify` 에서 비교해야 한다 → Step 4 에 그 코드가 있는 이유
- **재사용(replay)을 막지 못한다.** 유효한 토큰을 훔쳐 그대로 쓰면 통과한다. 무상태의 대가.
  막으려면 서버 상태(블랙리스트)가 필요하다
- **키 교체를 다루지 않는다.** 키를 바꾸면 기존 토큰 전부 무효 = 전원 로그아웃.
  실무에서는 토큰 앞에 **키 버전 1바이트**를 붙여 해결한다

## `TokenCipher` — 한 줄씩 왜 그렇게 썼나

| 코드 | 이유 |
|---|---|
| `base64Key` 에 `val` 이 **없다** | 생성자 파라미터를 `init` 에서만 쓰고 버린다. `val` 을 붙이면 **평문 키가 필드로 남아** 힙 덤프·`toString` 에 노출된다 |
| `key` 를 `init` 에서 한 번만 만든다 | `SecretKeySpec` 은 불변이고 스레드 안전. 매 요청마다 Base64 디코딩할 이유가 없다 |
| `random` 을 필드로 | `SecureRandom` 은 스레드 안전하고 **생성이 비싸다**(엔트로피 초기화). 재사용이 정석 |
| `Cipher` 는 **매번 새로 만든다** | `Cipher` 는 **스레드 안전하지 않다.** 필드로 빼면 동시 요청에서 상태가 섞여 조용히 깨진다. 여기만 유일하게 매번 생성 |
| `iv + encrypted` | Kotlin 의 `ByteArray.plus` = 두 배열을 이어붙인 **새 배열**. JS 의 `[...a, ...b]` 와 같다 |
| `GCMParameterSpec(TAG_BITS, decoded, 0, IV_SIZE)` | `(태그비트, 원본배열, offset, length)` 오버로드. `decoded.copyOfRange(0, 12)` 로 복사본을 만들 필요가 없다 |
| `doFinal(decoded, IV_SIZE, decoded.size - IV_SIZE)` | 같은 이유로 **암호문 부분만 offset 으로 가리킨다**. 배열을 두 번 자르지 않는다 |
| `withoutPadding()` | 패딩 `=` 를 뺀다. 쿠키에서 `=` 는 이름/값 구분자라 굳이 넣을 이유가 없다. `getUrlDecoder()` 는 패딩이 없어도 읽는다 |
| `String(bytes)` / `toByteArray()` | Kotlin 은 **기본 charset 이 UTF-8** 로 고정이다(Java 와 다르다). 플랫폼 기본에 끌려갈 걱정이 없다 |
| `companion object` + `const val` | 인스턴스마다 갖고 있을 값이 아니다. `const` 는 컴파일 타임 상수라 필드조차 만들지 않는다 |

## 예외를 여기서 잡지 않는다

`decrypt` 는 **암호 계층의 예외를 그대로 던진다.** `MessageException` 으로 바꾸는 건 **Step 4 의 `AuthService.verify`** 에서 한다.
`TokenCipher` 가 HTTP 상태코드(401)를 아는 건 계층 침범이다 — 이 클래스는 "바이트를 암호화한다" 만 알아야 한다.

`decrypt` 가 던질 수 있는 것:

| 상황 | 예외 |
|---|---|
| Base64 가 아닌 문자열 | `IllegalArgumentException` |
| 길이가 12바이트 이하 | `IllegalArgumentException` (우리 `require`) |
| 한 글자라도 위조 / 다른 키 | `AEADBadTagException` (`GeneralSecurityException` 의 자손) |

**⚠️ Kotlin 에는 multi-catch(`catch (e: A | B)`) 가 없다.** 그래서 Step 4 에서는 이렇게 된다:

```kotlin
val json = try {
    tokenCipher.decrypt(token)
} catch (e: Exception) {
    throw MessageException(ApiErrorCode.UNAUTHORIZED)
}
```

`Exception` 이 넓어 보이지만 여기서는 **의도한 것**이다. 복호화가 어떤 이유로 실패했든 클라이언트에게는 똑같이 401 이어야 하고,
사유를 구분해서 알려주면 Step 1 에서 세운 "실패 사유를 응답에 담지 말 것" 원칙을 어긴다. 상세는 로그에만.

**참고**: `spring-security-crypto` jar 하나만 넣으면 `Encryptors.stronger()` 로 같은 걸 얻을 수 있다.
직접 짜본 뒤에 비교해보면 IV·태그·모드가 각각 뭘 하고 있었는지가 선명해진다.
