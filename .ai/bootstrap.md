# AI 세션 공용 부트스트랩

이 저장소의 agent 작업 메모리와 프로젝트 관리 규칙의 canonical source다.
Claude Code는 루트 `CLAUDE.md`를 통해, Codex는 루트 `AGENTS.md`를 통해 이 문서를 읽는다.
두 진입점에는 이 규칙을 복제하지 않는다.

## 세션 시작 시 (항상)

아래 파일들을 먼저 읽고 작업을 시작한다.

* `.ai/memory/architecture/*.md` — 프로젝트 전체 구조/설계도
* `.ai/memory/rule/*.md` — 반드시 지켜야 하는 규칙
* `.ai/memory/convention/*.md` — 코드/작업 컨벤션

특정 도구나 agent 제품의 동작보다 `.ai/`에 기록된 프로젝트 규칙과 사용자의 현재 지시를
우선한다.

## 작업 진행 시

사용자가 특정 작업명이나 프로젝트명을 언급하면 해당 작업 폴더의 문서를 읽는다.
작업 방식은 frontend/backend 구분이 아니라 아래의 공통 흐름을 따른다.

* `.ai/projects/{작업명}/spec.md` — 배경 / 목적 / 확정한 설계 방향과 중요한 결정
* `.ai/projects/{작업명}/current.md` — 사용자에게 보이는 진행 체크리스트
* `.ai/projects/{작업명}/history.md` — 날짜별 append-only 진행 요약
* `.ai/projects/{작업명}/ref/` — 참고 파일과 지식 노트 (`ref/README.md`가 있으면 목록부터 읽음)
* `.ai/projects/{작업명}/request.md` — 필요할 때만 쓰는 아직 결정·해소되지 않은 열린 항목
* `.ai/projects/{작업명}/plan.md` — 지시서 검토 방식을 선택한 경우에만 쓰는 코드 수정 지시서

설계 결정은 `ref/`가 아니라 `spec.md`에 기록한다.
`request.md`를 사용했다면 대화로 해소된 항목은 `spec.md`에 반영한 뒤 제거한다.

## 기본 작업 흐름

일반적인 작업은 다음 흐름을 따른다.

```text
요구사항
   ↓
조사 / 설계
   ↓
필요한 의사결정
   ↓
spec.md 반영
   ↓
구현
   ↓
검증
   ↓
current.md / history.md 갱신
```

`plan.md`는 이 흐름의 필수 단계가 아니다.

## 설계와 사용자 확인

agent는 담당 범위 안에서 구현에 필요한 세부 사항을 합리적으로 판단할 수 있으며,
모든 구현 결정을 사용자에게 확인하지 않는다.

다만 아래처럼 구현 방향을 크게 좌우하거나 되돌리기 어려운 결정은 코드를 변경하기 전에
사용자와 방향을 합의한다.

* 페이지·메뉴 정보 구조를 바꾸는 일
* API 계약 변경
* 인증·권한 구조 변경
* 데이터 모델 또는 주요 상태 관리 방식 변경
* 새 라이브러리·외부 서비스·유료 의존성 도입
* 기존 기능 제거
* 데이터 손실 가능성이 있는 작업
* 넓은 범위의 UI 또는 시스템 구조 재설계
* 기존 `spec.md`의 중요한 결정과 충돌하는 변경

사용자가 이미 방향과 범위를 명확히 정한 일반 기능 구현, 버그 수정, UI 보완,
리팩터링 등은 agent가 합리적인 세부 결정을 내려 진행할 수 있다.

## 작업 방식

코드 작업은 다음 두 방식 중 하나로 진행한다.

### 자율 진행 — 기본

사용자가 별도의 작업 방식을 지정하지 않았다면 자율 진행을 기본값으로 사용한다.

`plan.md` 없이 확정된 설계와 프로젝트 규칙을 기준으로
agent가 구현·검증·문서 갱신까지 진행한다.

작업 규모나 역할 분리가 필요하면 멀티 에이전트를 사용할 수 있다.
사용자가 tmux 멀티 에이전트 작업임을 선언한 경우
`.ai/memory/rule/tmux-multi-agent.md`를 따른다.

멀티 에이전트의 역할 구성, 역할 간 통신, 병렬 작업, 하위 에이전트,
인수인계 및 의견 충돌 처리 등은 이 문서에서 중복 정의하지 않는다.

### 지시서 검토 — 선택

사용자가 코드 변경 내용을 항목·청크 단위로 직접 검토하면서 진행하고 싶은 경우
`plan.md`를 사용하는 지시서 검토 방식을 선택할 수 있다.

`plan.md`는 작업 규모나 위험도에 따라 agent가 자동으로 사용하는 문서가 아니다.
사용자가 구현 디테일에 직접 개입하고 싶은 경우 선택하는 작업 방식이다.

사용자가 지시서 검토 방식을 선택하면
`.ai/memory/rule/plan-md-workflow.md`를 따른다.

사용자가 별도로 선택하지 않았다면 `plan.md` 사용 여부를 매번 확인하지 않고
자율 진행한다.

## plan.md와 멀티 에이전트

`plan.md` 지시서 방식과 tmux 멀티 에이전트 방식은 동시에 사용하지 않는다.

두 방식의 목적이 다르다.

* `plan.md` — 사용자가 코드 변경 내용을 항목별로 직접 검토하고 개입하는 방식
* 멀티 에이전트 — 역할과 책임을 나누고 agent 간 협업과 자율 진행을 활용하는 방식

따라서 작업 방식은 다음처럼 구분한다.

```text
자율 진행
├─ 단일 Agent
└─ 멀티 Agent

지시서 검토
└─ 단일 Agent + plan.md
```

멀티 에이전트 작업에서는 `plan.md` workflow를 사용하지 않는다.
각 역할 Agent가 내부적으로 만드는 작업 계획이나 TODO는 사용자 검토용 `plan.md`로
간주하지 않는다.

작업 도중 두 방식 사이를 전환할 수는 있지만 동시에 활성화하지 않는다.

지시서 검토에서 자율 진행으로 전환할 때는 `plan.md`에만 남아 있는 확정 설계나
장기 보존할 지식이 있다면 `spec.md` 또는 `ref/`에 반영한다.

자율 멀티 에이전트 작업에서 지시서 검토 방식으로 전환할 때는 현재 병렬 작업을
안전한 지점에서 정리한 뒤 단일 Agent 작업으로 전환하고 `plan-md-workflow.md`를 따른다.

## 프로젝트 문서의 책임

작업 방식과 Agent 수에 관계없이 프로젝트 문서의 책임은 동일하다.

* `spec.md`

  * 배경, 목적, 확정한 설계 방향과 중요한 결정
* `current.md`

  * 현재 진행 상태와 남은 작업
* `history.md`

  * 실제 진행 내용을 날짜별 append-only로 기록
* `request.md`

  * 아직 결정되거나 해소되지 않은 열린 항목
* `ref/`

  * 작업에 필요한 참고 자료와 재사용 가능한 지식
* `plan.md`

  * 지시서 검토 방식에서 현재 검토 중인 코드 수정 지시

설계 결정은 `spec.md`에 기록하며, 장기간 유지할 지식을 `plan.md`에만 남기지 않는다.

## 구현 완료 후

구현과 검증이 끝나면 실제 결과에 맞게 프로젝트 문서를 갱신한다.

* `current.md`

  * 완료한 항목을 `- [x]`로 체크한다.
  * 완료 항목을 삭제하지 않는다.
* `history.md`

  * 작업이 한 단계 진전될 때마다 날짜별 요약을 맨 아래에 append한다.
  * 기존 기록은 수정하거나 삭제하지 않는다.
* `spec.md`

  * 구현 과정에서 확정된 중요한 설계 결정이 있으면 반영한다.
* `request.md`

  * 해소된 항목은 필요한 결정을 `spec.md`에 반영한 뒤 제거한다.
* `ref/`

  * 이후에도 재사용할 가치가 있는 조사 결과나 배경 지식이 생겼다면 주제별로 정리한다.
* `plan.md`

  * 지시서 검토 방식을 사용했다면 `.ai/memory/rule/plan-md-workflow.md`의
    종료·재사용 규칙을 따른다.

## 공용 운영 규칙

* **request → spec 승격**: `request.md`의 항목이 대화로 해소되면 필요한 내용을
  `spec.md`에 반영하고 해당 항목을 제거한다.
* **history 기록**: 작업이 한 단계 진전될 때마다 해당 `history.md` 맨 아래에 날짜별
  요약을 append한다. 기존 기록은 수정하거나 삭제하지 않는다.
* **current 갱신**: `current.md`의 할 일이 완료되면 `- [x]`로 체크한다.
  완료 항목을 삭제하지 않는다.
* **plan은 선택 사항**: `plan.md`는 모든 코드 작업의 필수 단계가 아니며
  지시서 검토 방식에서만 사용한다.
* **멀티 에이전트와 plan 분리**: tmux 멀티 에이전트 작업에서는
  `plan.md` workflow를 사용하지 않는다.
* **새 작업 시작**: `.ai/projects/_TEMPLATE/`를 복사하여
  `.ai/projects/{작업명}/`을 만든다. `request.md`, `plan.md`, `ref/`는 필요할 때만
  추가한다.
* **코드와 문서의 범위**: 요청이 문서/메모리 관리라면 코드 파일을 수정하지 않는다.
  코드 변경은 현재 선택된 작업 방식과 해당 workflow의 승인 범위를 따른다.

## 경로 기준

`.ai/`가 프로젝트 지식과 공용 workflow의 canonical source다.

Claude Code의 `settings.local.json`처럼 특정 도구의 로컬 설정은 `.ai/`로 옮기지 않고
도구 전용 위치에 둔다.
