# plan.md 지시서 작업 방식

코드를 여러 파일에 걸쳐 수정하는 작업은 **`plan.md` 지시서**를 거쳐 진행한다.
agent가 코드를 곧바로 고치는 대신, "무엇을/어디를/어떻게/왜" 를 `plan.md` 에 옮겨넣어
사용자가 검토하고, 반영한 뒤 agent가 정합성을 확인하는 사이클로 돈다.

## 1. 작업 단위 = 섹션 (필요 시 청크)

- 큰 작업은 **섹션 단위로 쪼개서**, 각 섹션을 `plan.md` 로 진행한다.
- 한 섹션이 너무 크면 **청크로 한 번 더 나눠서** (중첩 분할) 진행한다.
- `plan.md` 는 해당 작업 폴더에 둔다: `.ai/projects/{작업명}/plan.md`.
- 실제 진행은 그 안의 **항목 단위**로 아래 사이클을 반복한다.

## 2. 항목별 진행 사이클

매 항목마다 다음 순서로 돈다:

1. **제시 (agent)**
   `spec.md` 를 토대로, 다음 수정할 코드를 **"어느 파일 / 어디를 / 어떻게 / 왜"** 와 함께 `plan.md` 에 제시한다.
   이 단계에서는 **코드를 직접 수정하지 않는다.**

2. **검토 · 반복 (사용자 ↔ agent)**
   사용자가 `plan.md` 를 검토하며 궁금한 건 물어보고, 그에 따라 **반복해서 수정·추가**한다.

3. **반영**
   - **기본**: 사용자가 직접 코드에 반영한다.
   - **트리거**: 사용자가 **`"플랜 적용해줘"`** 라고 하면, 그 반영을 **agent가 직접 코드에 적용**한다. (아래 4절)

4. **정합성 검사 (agent)**
   반영된 코드에 **빠진 게 없는지**, 코드가 **주입된 곳 위주로** 점검한다.
   (섹션/청크 전체의 아귀가 맞는지 — 누락·중복·서로 안 맞는 부분 확인)

## 3. 트리거: `"플랜 적용해줘"`

3단계(반영)에서 사용자가 `plan.md` 내용에 만족하면 **`"플랜 적용해줘"`** 라고 말한다.
이 말의 의미는 **"사용자가 직접 하던 수동 반영을, agent가 대신 코드에 직접 적용해라"** 이다.
→ 이 트리거가 곧 **코드 직접 수정에 대한 명시적 승인 신호**다. ([[git.md]] 의 변경 전 승인 원칙과 동일 선상)

### 안전장치 (오발동 방지)

- 직접 적용은 **`plan.md` 가 존재하고 검토가 끝난 상태**에서만 발동한다.
- 문맥상 애매하거나 `plan.md` 가 비어 있으면, **직접 적용하지 말고 먼저 확인**한다.
- 트리거가 나오기 전까지는 (1~2단계) 코드를 직접 고치지 않는다.

## 4. 적용 후 처리 — plan.md 비우고 재사용

- 한 항목의 반영·정합성 검사가 끝나면 `plan.md` 의 **내용만 비우고**, 다음 항목/청크/섹션에 **재사용**한다.
- **파일 자체 삭제는 프로젝트 전체가 끝났을 때만** 한다. (작업 중 삭제 금지)

## 원칙

- 기본값은 "agent는 지시서만 쓰고, 사람이 반영" → 트리거로 그 반영을 agent에 위임하는 구조.
- 애매하면 **직접 적용해도 되는 승인 상태인가?** 로 판단 → 아니면 지시서만 쓰고 대기.
- 반영이 끝나면 항상 agent가 정합성 검사로 마무리한다.

> 진행 요약은 각 작업의 `history.md` 에 쌓는다 — append-only 규칙은 [[history-append-only]] 참고.
